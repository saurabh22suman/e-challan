## What was built

### Shared contracts — `packages/contracts/src/domain.ts`

Authority: replacement specification v0.1 sections 4–6. Exported from the
package root via `export * from './domain.js'`, so no consumer reaches into
package internals.

| Export | Rule |
|---|---|
| `ChallanSubmissionSchema` | `strictObject`. `operationId` UUID (idempotency key), `vehicleNumber`, `gatePassNumber`, `driverName`, `departmentId`, optional `contractorId`, `vehicleTypeId`, distinct nonempty `violationIds`, optional `remarks` (≤2000), `photoIds` (1–4 distinct UUIDs), `acknowledgement` |
| `AcknowledgementSchema` | discriminated union: `{kind:'signed',signatureId}` or `{kind:'refused',reason,witnessName,witnessStaffId}`; both refusal fields mandatory (E2.14) |
| `ResolutionActionSchema` | `{action,remarks}`, action ∈ the four approved codes, remarks nonblank for **all** including `custom`; strict, so the rejected `customActionName` is an error |
| `ReviewTransitionSchema` | discriminated union on `to`: `Under Review` (optional `reason` for reopening), `Resolved` (action+remarks), `Cancelled` (reason) |
| `SeveritySchema` / `ChallanStatusSchema` / `RoleSchema` | strict approved vocabularies; `Guest`, `Pending`, `Extreme` all rejected |
| `deriveChallanSeverity` | highest-of-set, order independent; throws on empty or unapproved severity |
| `recommendedActionForOccurrence` | 1→`warning_issued`, 2→`safety_counselling_completed`, 3+→`referred_to_department_contractor`; throws on non-positive or fractional counts |

Normalisation is transform-then-validate: registration uppercased with all
whitespace removed, then matched against the two approved patterns (conventional
`^[A-Z]{2}\d{1,2}[A-Z]{1,3}\d{1,4}$`, BH `^\d{2}BH\d{4}[A-Z]{1,2}$`); gate pass
uppercased and trimmed, then restricted to `^[A-Z0-9/-]{1,64}$` so internal
whitespace fails; names/remarks trimmed then bounded.

`strictObject` is the load-bearing part: a client-supplied `severity`, `status`,
`challanNumber`, `issuedAt`, `marshalId` or `locationId` is **rejected**, never
silently stripped. That is the approved "reject forged attribution" rule.

### API adapter — `apps/api/src/domain/validation.ts`

`validateChallanSubmission(input)` returns exactly `ChallanSubmissionSchema.parse(input)`.
Internal plumbing only; there is deliberately **no** route exposing validation or
issuance. Its doc comment enumerates what it does **not** prove: master
activeness, Other-remarks coupling, evidence existence/ownership/capture, witness
role qualification, actor/post/shift authorisation, duplicate/repeat
acknowledgement, occurrence counting, numbering and issuance. Those need real
domain context in their later tasks and are not claimed here.

### Relational schema — `apps/api/src/db/schema.ts`

21 domain tables added after the retained foundation table. Field dictionary and
relationship decisions, all enumerated here as the plan requires:

| Area | Decision |
|---|---|
| Identity | UUID PKs everywhere, independent of display numbers. `demo_source_id` preserves fixture traceability; fixture IDs are never treated as approved UUIDs |
| Timestamps | `timestamptz` UTC instants. Site-day, 90-day and 15-minute windows evaluate in `Asia/Kolkata`; PostgreSQL preserves the instant, and nothing claims it preserves the original textual offset |
| Attribution (B-04) | `challans` records `issued_by_user_id`, `post_id`, `shift_id`, `gate_id`, `location_id` separately, so post/shift/session attribution is auditable rather than inferred |
| Masters (B-05) | Issued rows keep **both** the master reference and immutable snapshots (`label_snapshot`, `severity_snapshot`, `default_action_snapshot`; plus department/contractor/vehicle-type label snapshots on `challans`). Later edits or deactivation cannot change issued meaning |
| Deletion | All FKs onto masters/identities are NO ACTION/RESTRICT, so deleting a master is refused instead of cascading away historical challans. Only pure children cascade (violations, evidence, signatures, refusals, actions, audit) |
| Registry (B-06) | `gate_pass_records` with unique normalised `gate_pass_number`, one driver/vehicle association, validity window, `registry_status`; `gate_pass_locations` for visibility. Issuance location always comes from the authorised post, never copied from the pass |
| Normalisation | `vehicles.registration_number` unique and uppercase-normalised; `gate_pass_records.gate_pass_number` unique and uppercase-normalised |
| Constraints | UNIQUE on `users.username`, `vehicles.registration_number`, `gate_pass_records.gate_pass_number`, `challans.challan_number`, `evidence(challan_id,ordinal)`; PK on `challan_violations(challan_id,violation_type_id)`, `user_locations`, `gate_pass_locations`; CHECK on `challans.status`, `challans.occurrence_number ≥ 1`, `violation_types.severity`, `challan_violations.severity_snapshot`, `challan_actions.to_status`, `users.role`, `evidence.ordinal 1..4`, non-empty audit `event_type` |
| Indexes | `challans(gate_pass_number, issued_at)` for the 90-day repeat window, `challans(vehicle_registration_number, location_id, issued_at)` for the independent 15-minute duplicate window, `challans.status`, per-master `is_active`, `challan_actions(challan_id)`, `audit_events(challan_id)` and `(created_at)` |
| Evidence | Object **references** only (`object_key`, ordinal, optional size/type, `captured_at`); the database stores keys, not binaries. No validated-blob or device claim is encoded |
| Audit | `audit_events` append-only; no update/delete path, and it survives cancellation and reopening |
| Not encoded | Severity derivation, occurrence counting, recommendation tiers, numbering and transition legality are pure helpers or later services. No unapproved business rule was added as a database convenience constraint |

`users` has **no password column** at all: E1.5 credentials belong to F-02, and
adding an unused column would be an unapproved authentication decision.

### Seed adapter — `apps/api/src/db/seed-domain-demo.ts`

`seedDomainDemoDatabase(connectionString)`, plus a **separate** command
`db:seed:domain`. The foundation `seedDemoDatabase` / `db:seed:demo` adapter is
untouched and still seeds its own row.

- Target guard runs **before any connection or write**, via
  `assertIsSeedAllowedDatabase`; `…/production` is refused.
- Deterministic UUIDs derived from fixture identifiers (documented SHA-256 →
  RFC 4122 v5 mapping), so a repeated seed never changes a row identity.
- Every write is an upsert in one transaction, so repeat invocation converges:
  10 drivers, 9 vehicles, 10 gate-pass records, 14 challans, stable IDs.
- **No evidence rows and no signature rows.** The fixture's `photoCount` and
  `signatureState` are display metadata; the specification states metadata counts
  are not evidence. Real blobs arrive with I-02–I-06.
- **Refusals are inserted** for the two explicit refusal fixtures, because those
  carry real structured data (reason, witness name, witness staff ID).
- `violation_types.default_action` is left **NULL**: the fixture supplies and
  approves no default action, so none was invented.
- Occurrence numbers and recommendations are *derived* by applying the approved
  90-day rule and recommendation tiers to the fixture's own timestamps. Observed
  result, e.g. `DEMO-GP-0001`: Jun 23 → 1, Aug 22 → 2, Sep 24 → 2 (the Jun
  record is 93 days earlier and correctly falls outside the window), Oct 1 11:50
  → 3, Oct 1 11:58 → 4. Repeat is keyed on the gate pass, not the location, so the
  dispatch-gate record still counts — matching the approved rule.
- Action rows exist for `Resolved`/`Cancelled` display states so the append-only
  history is coherent; each carries `demo_source_id` and synthetic remarks
  stating it is not an operational record.

### B — Repair relational invariants (incremental, additive only)

Two new migrations. `0000`–`0002` were **not** edited, reordered or re-tagged; their
hashes still match the baseline, because they are applied history.

**`0003_certain_zarda.sql`** — corrective invariants, generated by drizzle-kit and
then reordered by hand for three documented reasons (FK target ordering, backfill,
guard). No generated statement was dropped or weakened:

1. `posts.gate_id uuid` added, then **backfilled** from the unambiguous gate at the
   post's location, then a `DO` guard that **raises** if any post remains
   unassociated rather than silently leaving a NULL.
2. `violation_types.severity` → `SET NOT NULL`, old permissive CHECK dropped and
   replaced with `severity IN ('Minor','Major','Critical')`. No `Unknown` severity
   invented; all seven fixture masters already carry a display severity.
3. `gates UNIQUE(id, location_id)` as a composite reference target.
4. `posts UNIQUE(gate_id)` (a gate is never claimed by two posts) and
   `posts UNIQUE(id, gate_id)` as a composite reference target.
5. `posts.gate_id → gates.id` (FK) and `posts(gate_id, location_id) →
   gates(id, location_id)` (composite FK), so a post can never be bound to a gate at
   another location.
6. `challans(post_id, gate_id) → posts(id, gate_id)` and
   `challans(gate_id, location_id) → gates(id, location_id)`, so a challan's
   attribution is DB-owned rather than three independent references that could each
   point at a valid row while describing an impossible pairing.
7. **R1 canonical checks:** `vehicles.registration_number = upper(regexp_replace(…,'\s','','g'))`
   and `gate_pass_records.gate_pass_number = upper(…) AND gate_pass_number !~ '\s'`.
   Combined with the pre-existing UNIQUE constraints this makes identity unique by
   canonical value, not raw text. The two approved rules stay distinct: registration
   strips all whitespace, gate pass rejects internal whitespace rather than
   stripping it.

**`0004_lowly_power_man.sql`** — `ALTER TABLE posts ALTER COLUMN gate_id SET NOT NULL`,
generated unmodified, confirming every existing post was successfully backfilled.

Migration effects: two additive migrations on the demo database. Backfill verified
