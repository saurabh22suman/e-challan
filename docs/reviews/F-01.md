## Findings requiring correction

### R1 — High: PostgreSQL permits duplicate normalised identities

References: `apps/api/src/db/schema.ts:238–248,251–277`;
`apps/api/drizzle/0002_groovy_charles_xavier.sql:19,21`;
`specs/002-demo-domain/spec.md:91–92,105–106`.

The approved interface requires normalised vehicle/pass uniqueness in PostgreSQL,
not merely Zod. Current UNIQUE constraints compare raw text, while normalisation
exists only in the client contract/seed path. A second row may therefore contain
the same logical registration or gate-pass number with changed case/whitespace.

Real isolated-DB reproduction inside a rolled-back transaction:

```text
vehicles accepted both: TN09BK3542 and " tn09bk3542 "
gate_pass_records accepted both: DEMO-GP-0007 and " demo-gp-0007 "
```

The SQL UPDATEs succeeded, and queries using approved normalisation returned two
matches. The existing exact-text duplicate tests pass and do not detect this.

Implementer: enforce the normalised invariant at the DB boundary, using canonical
value constraints plus uniqueness or equivalent expression/generated-key
uniqueness. Preserve existing demo data and stable IDs. Planner: add case and
whitespace variant SQL rejection tests that accept the appropriate uniqueness or
canonical-value error, plus positive distinct canonical values. Do not change the
approved normalisation rule to accommodate raw duplicates.

### R2 — Medium: active violation masters can have no severity

References: `apps/api/src/db/schema.ts:210,218–220`;
`apps/api/drizzle/0001_curvy_squadron_supreme.sql:212–219`;
`apps/api/drizzle/0002_groovy_charles_xavier.sql:29`.

`violation_types.severity` is nullable, and its CHECK explicitly permits NULL.
The approved spec requires one master severity per violation, derived into the
issued record; NULL is not a member of Minor/Major/Critical.

In the same guarded DB probe, `UPDATE violation_types SET severity=NULL WHERE
is_active=true RETURNING id,severity` succeeded for **all six active masters**.
The transaction was rolled back. The supplied test only rejects the string
`Extreme`, leaving this missing-value case uncovered.

Implementer: require an approved severity value for violation masters, without
changing the approved master data or inventing an Unknown severity. Planner: add
NULL/missing-severity insert/update rejection coverage alongside approved values.
This finding is about severity, not the separately documented nullable default
action for fixture data.

### R3 — Medium: authoritative post-to-gate relationship is not represented

References: `apps/api/src/db/schema.ts:149–187,322–337`;
`apps/api/src/db/seed-domain-demo.ts:160–202,483–485`;
`specs/002-demo-domain/spec.md:96–101`; approved replacement sections 4/7/8.

The approved model binds issuance location/gate to the authorised post and
requires post/shift/gate/location relationships. The seed fixture explicitly
contains `gate.postId`, but persisted `posts` and `gates` each retain only a
location reference. Neither table nor a join table stores their association.
The seed transiently reconstructs it while inserting historical challans.

Inspecting actual PostgreSQL columns confirms there is no gate FK on posts or
post FK on gates. Once more than one gate exists at a location, location matching
alone cannot establish which gate a post belongs to. Separate challan FKs can
all reference existing rows without establishing the intended relationship.

Planner: specify the authoritative persisted association and expected consistency
checks for the existing demo post/gate mappings. Implementer: preserve that
association in schema/seed and document how current post resolves the authorised
gate/location and which consistency constraints are DB-owned versus API-owned.
Do not defer the missing relationship to an ad hoc hard-coded F-02 mapping.
