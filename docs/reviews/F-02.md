## R1 — High: client gates check authentication but not role

References: `apps/tablet/src/App.tsx:37–40`, `apps/admin/src/App.tsx:36–39`,
both clients' session providers. Authority: PRD E1.1 and the retained owner auth
decision (Marshal tablet; Supervisor/Admin dashboard).

Both gates render on `status === 'authenticated'` without checking the stored
identity's role. Independently observed: Marshal login displays the admin
foundation heading; Supervisor login displays the tablet foundation heading.
Thus the correct role interface is not protected. This finding does not claim
that API record-scope enforcement was bypassed.

Planner: add wrong-client role cases for login and restoration. Implementer:
enforce the approved role boundary on both paths with clear feedback or approved
routing, retaining independent server-side permissions.

## R2 — High: stale restoration erases a newer successful login

References: `apps/tablet/src/auth/session.tsx:66–100`,
`apps/admin/src/auth/session.tsx:68–102`.

The mount request's cancellation flag changes only on effect cleanup. Signing
in does not invalidate pending restoration. A delayed anonymous lookup therefore
clears the newly issued token/identity after login succeeds. The browser probe
reproduced heading count 1 → 0 and removal of the new token in both clients.

Planner: prepare deterministic delayed-response acceptance. Implementer: order
transitions so obsolete restoration/login responses cannot replace newer session
state, including logout; handle rejected/malformed restoration bodies cleanly.
Verify login remains usable when the initial lookup is slow.

## R3 — High: Marshal session can omit required active-shift attribution

Reference: `apps/api/src/auth/service.ts:224–236`. Authority: AUTH-05 and the
feature's post/shift resolution requirement.

Zero compatible active shifts leaves `shift` null and succeeds. The real-DB
probe deactivated shifts and received 200, a token and `shift: null` for Marshal.
Required attribution is not enforced.

Planner: add zero-shift refusal and ambiguous-context acceptance. Implementer:
fail closed when a required compatible shift is unavailable, preserving single
candidate resolution and ambiguity refusal. Complete the tablet post/shift
selection specified at `specs/003-demo-auth/spec.md:103–107`: currently the login
screen and `signIn` accept only username/password, so ambiguity cannot be resolved
from the UI. Verify explicit authorised context without guessing.

## R4 — Medium: malformed IDs expose SQL in 500 responses

Reference: `apps/api/src/auth/routes.ts:169–175`.

Arbitrary `:id` text reaches a PostgreSQL UUID predicate. With a valid token,
`GET /challans/not-a-uuid` returns 500 containing the Drizzle query and parameters.
The comment promising a malformed-ID 404 is not implemented.

Planner: add malformed-ID acceptance. Implementer: validate before querying,
return the agreed controlled error and avoid exposing query details in unexpected
API errors.
