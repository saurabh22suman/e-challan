## Findings

### R1 — High: clean-checkout CI typecheck fails before shared packages are built

References: `.github/workflows/ci.yml:98–105`, `package.json:19`,
`packages/contracts/package.json:9–14`, `packages/theme/package.json:9–14`.

Both shared packages export declarations from `dist/`, but CI calls `pnpm
typecheck` before any shared-package build. Recursive typechecking uses `--noEmit`
and does not produce these declarations. Existing local artifacts mask this.

Reproduced in `/tmp/opencode/s01-review-7ysje71t`, a disposable copy excluding all
`dist/`, TypeScript caches and local `.env`, with installed dependencies retained:
`pnpm typecheck` exits 2. Admin reports TS2307 for `@echallan/theme` and
`@echallan/contracts`. `pnpm build:packages` followed by `pnpm typecheck` passes
in that same copy. This is a package-resolution failure, not an unavailable
external prerequisite. It prevents SET-01 and SET-04 acceptance.

Implementer: establish a reliable shared-package build prerequisite for the
documented gates and CI, then verify from a workspace without generated artifacts.
Planner: add a clean-artifact gate-order regression check; the existing smoke
tests only inspect command/workflow declarations and do not catch this failure.

### R2 — Medium: boundary gate permits app-package subpath imports

Reference: `tools/check-boundaries.mjs:171`.

The check uses `APP_PACKAGES.includes(specifier)`, matching only a bare app name.
A temporary tablet fixture importing `@echallan/admin/src/App` returns exit 0 and
reports no forbidden imports. The same problem applies to other app subpaths and
to static imports, exports and literal dynamic imports using those specifiers.
This does not enforce the stated app-to-app boundary (SET-03).

Implementer: recognize both the exact package name and slash-delimited subpaths.
Planner: add subpath-import negative fixtures for the boundary directions; retain
the approved existing baseline until a documented planner revision.

### R3 — Medium: admin-only widgets are rejected inside the admin app

References: `tools/check-boundaries.mjs:221–230`, `README.md:128–130`.

The widget restriction has no owner/surface condition. A temporary
`@echallan/admin` fixture importing `@mui/x-data-grid/DataGrid` exits 1 with an
`admin-only-widget` violation, despite the declared rule limiting this restriction
to tablet/shared client code. It would block valid admin work under root lint.

Implementer: scope the restriction to tablet and shared client packages while
preserving their prohibitions. Planner: add an admin-positive widget fixture plus
tablet/shared-negative coverage.

### R4 — Medium: claimed lazy-import failure sensitivity is not reproduced

References: `apps/tablet/src/__tests__/foundation.test.tsx:59–68`,
`apps/admin/src/__tests__/foundation.test.tsx:60–69`,
`docs/handoffs/S-01.md:134–139`.

In the disposable copy, replacing each `React.lazy` import with an eager static
import, while keeping conditional route rendering, leaves both suites green:
tablet 4/4, admin 4/4. These tests prove navigation and conditional rendering;
they do not prove code splitting. This contradicts the handoff's claim that an
eager-import mutation made both named tests fail. The current source really does
use lazy imports and the production manifest has a separate dynamic route chunk;
the defect is in the claimed verification evidence and regression sensitivity.

Planner: define a meaningful lazy-loading/build-manifest assertion that fails on
the eager-import mutation. Implementer: correct the evidence record and rerun the
approved check. Do not merely rename the tests or claim the current assertions
establish lazy loading.
